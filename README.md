# Testing

Minimal static Vite web page with release/update support. No UI framework or native wrappers.

```sh
npm ci
npm run dev
# Validate and build:
npm run check && npm test && npm run build
```

## Releases

Exactly two manual workflows in Actions:

1. **Web — Test Build**: run on any branch. Tests, syntax checks and builds; uploads a branch/SHA/version-labelled artifact retained for seven days. Creates no version or release.
2. **Web — Release**: run on the default branch. For another branch explicitly tick **confirm**. Tests and builds, creates the next tag and GitHub Release, uploads `Testing-X.Y-web.zip`, then deploys to GitHub Pages. Web is the only/primary platform; there are no add-ons.

Enable **Settings → Pages → Source → GitHub Actions** before releasing. Repository Actions must be allowed to write contents and deploy Pages. Only the built-in `GITHUB_TOKEN` is used; no personal token or signing secrets are needed. Builds use Node 22 and npm caching.

Versions start at `v1.0`, advancing numerically through `v1.9` to `v2.0`. Invalid tags are ignored. Optional **version_override** accepts `3` (v3.0) or `1.4`. Existing tags/releases are never reused; lower overrides warn. The next automatic version always follows the highest valid tag. Test builds label with the next version without consuming it. Tags, not package commits, are authoritative; CI injects package version `X.Y.0`, app version `X.Y`, and commit SHA into the build.

The release title and notes are generated by GitHub. Each tag points to the exact built commit. Release creation happens before Pages deployment: if deployment fails, the release remains valid; fix Pages settings and rerun only the failed deployment step/job as appropriate (do not reuse or delete its tag). A new full run creates another version. GitHub concurrency serializes active release runs; avoid queueing many releases at once because GitHub may replace pending runs.

## Updates and data

On page load, the app checks the latest release once, reusing its locally saved time/result for two minutes. Manual **Check for updates** bypasses that cache and is disabled during a check. No timers, polling, focus or resume checks. Automatic offline/rate-limit failures are silent; manual failures show a short retry message.

Only strictly newer valid release versions qualify. A forgiving `-web.zip` asset match distinguishes available from preparing. The app checks deployed `version.json` without browser cache and offers Reload only once a newer build is actually deployed. Reload uses a cache-busting URL. A web archive alone is not an installed deployment.

Only the last check timestamp/result is stored in browser localStorage. No app files, logs or native data directories are used. Web needs no signing.

### Hosting/cache limitation

Vite fingerprints JavaScript assets. No service worker is registered (and therefore none can serve stale HTML). Metadata fetches bypass caches and HTML declares no-cache as a best-effort hint. **GitHub Pages does not allow custom HTTP cache headers**, so it cannot guarantee uncached HTML or immutable hashed assets. For strict HTTP cache policy, host the release archive on a server configured with:

- HTML, `version.json`, and any future service-worker script: `Cache-Control: no-store`.
- Hashed `/assets/*`: `Cache-Control: public, max-age=31536000, immutable`.

Configure the Vite base path for that host when building. GitHub Pages builds use the repository-name path.
